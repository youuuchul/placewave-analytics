# ranker: 검색 순위 모델

Placewave 검색의 새 랭킹(v2)을 이루는 두 부분, **검색어 해석**과 **순위 모델(LightGBM LambdaRank)** 의 코드·설계·오프라인 평가다. 보고서 묶음 「검색 품질 개선」의 4단계 `순위 모델 설계·오프라인 평가`(대시보드 `?page=reports&r=ranker-model`)가 이 폴더의 산출을 화면에 올린다.

## 1. 구조

    검색어
      → ① 해석   소문자·공백·구분자(· /) 정리 → 동의어 사전 → 공간명 앞부분 일치      query.py · synonyms.json
      → 정식 이름 + 의도 유형(장르 · 상권 · 행사 유형 · 공간명 · 해석 못 함)
      → 후보(공간·행사)
      → ② 순위 모델   (검색어, 후보) 피처 14개 → LightGBM LambdaRank 점수 → 상위 10      features.py · train.py

- **① 해석**: 기존 랭킹(v1)은 정식 이름과 글자가 같아야 찾았다. 실패 검색어(보고서 1단계)는 대부분 줄임말·영문 표기·한 동네 이름이었다. 그래서 입력을 정규화하고 동의어 사전으로 정식 이름에 연결한다. 예: `edm` → 일렉트로닉, `연남` → 홍대·합정·연남, `홍대 합정 연남` → 홍대·합정·연남. 사전에 없고 2글자 이상이면 공간명 앞부분과 맞춘다.
- **② 순위 모델**: 라벨(관련도 0~3, 보고서 2·3단계)로 순서를 학습한다. 기존 랭킹은 키워드 일치·인기 위주라 관련도와 거의 무관하게 섞였다.

## 2. 학습 데이터

`staging.ml_ranker_pairs` (SQL `bigquery/sql/08_ml_ranker_pairs.sql`)

| 항목 | 값 |
|---|---|
| 라벨 | 2026-07-06(A/B 설계서 작성일) 전에 제출된 최종 라벨 47,775건 |
| 단위 | 검색어 × 후보 11,195쌍, 검색어 563개(관련 후보가 있는 검색어 290개) |
| 정답 등급 | 쌍별 최종 라벨 등급 평균을 반올림한 0~3 |
| 교차 검증 묶음 | 검색어 단위 5묶음, `FARM_FINGERPRINT(query_norm) mod 5` |
| 인기 | 학습 마감 전 티켓 신청 수(행사는 그 행사, 공간은 그 공간의 모든 행사) |

7/6 전에는 기존 랭킹만 있어서, 결과가 나온 검색어(= 정식 이름)에만 평가 후보와 라벨이 있다. 줄임말 검색어는 정렬 평가에 들어가지 않고, 해석 평가는 검색 로그로 따로 한다(§4).

## 3. 피처와 모델

| 묶음 | 피처 | 설명 |
|---|---|---|
| 검색어 | `query_intent`, `query_term` | 의도 유형, 해석한 정식 이름(범주형) |
| 후보 속성 | `item_type`, `item_genre`, `item_venue_type`, `item_event_type` | 후보 종류·장르·공간 유형·행사 유형(범주형) |
| 의도·속성 일치 | `genre_match`, `region_match`, `event_type_match`, `host_has_event_type`, `name_match`, `named_area_genre` | 검색 의도와 후보 속성이 맞는가 |
| 거리 | `region_dist_km` | 검색 상권 중심까지 거리(상권 검색만) |
| 인기 | `popularity_log` | log(1 + 학습 마감 전 신청 수) |

노출 순위·클릭은 넣지 않는다. 기존 랭킹이 만든 순서를 그대로 배우게 되기 때문이다(위치 편향).

| 하이퍼파라미터 | 값 |
|---|---|
| 목표 | `lambdarank` (NDCG 최적화), 이득 2^등급 − 1 |
| 학습률 · 반복 | 0.05 · 200회 고정 |
| 잎 · 최소 잎 크기 | 15 · 20 |
| 행 표본 · 피처 표본 · L2 | 0.8 · 0.9 · 1.0 |
| 재현성 | `seed=20260706`, `deterministic=True`, `num_threads=1` |

반복 수는 조기 종료 대신 고정했다. 묶음마다 조기 종료 판단용 검색어가 25개 남짓이라 멈추는 지점이 3회~76회로 흔들렸다. 고정 반복의 민감도는 작다(교차 검증 NDCG@10: 100회 0.8715 · 200회 0.8726 · 400회 0.8742).

## 4. 오프라인 평가

**① 해석**: 기준선 2주(2026-06-22 ~ 07-05, 실험 설계서와 같은 기간) 서버 검색 요청 4,423건

| 지표 | 기존 랭킹 | 새 해석 적용 시 |
|---|---|---|
| 결과 0건 요청 | 1,166 (26.4%) | 151 (3.4%) |
| 기존 0건 중 정식 이름에 연결 | — | 1,015 (87.0%) |

남은 151건은 공간명 오타처럼 사전에 없는 입력이다. A/B 실험군의 실제 결과 0건 비율은 3.1%였다.

**② 순위 모델**: 5묶음 교차 검증, 관련 후보가 있는 검색어 290개, NDCG@10

| 의도 | 검색어 | 기존 정렬(인기순) | 순위 모델 |
|---|---|---|---|
| 전체 | 290 | 0.570 | 0.873 |
| 공간명 | 269 | 0.572 | 0.864 |
| 상권 | 10 | 0.573 | 0.965 |
| 장르 | 6 | 0.590 | 0.977 |
| 행사 유형 | 5 | 0.438 | 1.000 |

묶음 간 표준편차 0.042. 학습 데이터 전체로 맞춘 최종 모델의 학습 내 NDCG@10 은 0.920(교차 검증과의 차이가 과적합 정도).

**피처 묶음 제거 실험**(교차 검증 NDCG@10, 전체 피처 0.873): 의도·속성 일치 제거 0.638 · 후보 속성 제거 0.858 · 인기 제거 0.866 · 검색어 제거 0.871 · 거리 제거 0.873. 순서를 정하는 것은 검색 의도와 후보 속성이 맞는가이고, 인기는 같은 등급 안의 순서를 정한다. 거리는 상권 일치와 겹쳐 빼도 차이가 없다.

## 5. 실행

macOS 는 LightGBM 이 OpenMP 를 쓰므로 한 번 `brew install libomp`.

    uv run --group ml python -m ranker.train              # BigQuery 에서 입력을 읽어 학습·평가·산출물 쓰기
    uv run --group ml python -m ranker.train --cache      # 지난번 받은 입력(data/model/input_*.csv)으로
    uv run --group ml python -m ranker.train --ablate popularity   # 피처 묶음 하나를 빼고 비교만
    uv run --group ml python -m ranker.sim_check          # A/B 시뮬레이션의 랭킹 수준과 비교(§6)

파이프라인 안의 순서(`bigquery/load_all.sh`):

1. 6단계 `staging.ml_ranker_pairs` 생성
2. `ranker/train.py` → `data/model/ml_query_parse.csv` · `ml_ranker_scores.csv` · `ml_ranker_features.csv`, `ranker/artifacts/`
3. 1단계 `raw.ml_query_parse` · `ml_ranker_scores` · `ml_ranker_features` 적재
4. 7단계 `marts.ranker_eval` · `ranker_query_eval` · `ranker_feature`
5. 8단계 검사 C22(채점 = 해석된 학습 쌍) · C23(평가 마트 = 학습 쌍) · I10(산출 버전 하나 · 중요도 합 1 · 검색 로그 검색어 전부 해석) · I11(새 해석 의도 = 검색 로그 의도 분류)

라벨이 바뀌어 학습 쌍이 달라졌는데 다시 학습하지 않으면 C22·C23 이 실패해 파이프라인이 멈춘다. `train.py` 도 해석 결과가 검색 로그의 의도 분류와 하나라도 다르면 중단한다(2,139개 검색어 일치).

산출물: `artifacts/model.txt`(LightGBM 텍스트 모델, 검색어 전체로 다시 맞춘 최종본) · `artifacts/model_card.json`(데이터·피처·범주 사전·하이퍼파라미터·평가·제거 실험). 대시보드는 마트를 거친 값만 쓴다(`dashboard/scripts/extract.py`).

## 6. 데이터 생성기와의 관계

이 저장소의 로그는 데이터 생성기(`generator/`)가 만든 합성 데이터다. 생성기는 A/B 의 기존·새 랭킹을 이 모델의 점수가 아니라 '참 관련도 + 정렬 잡음'으로 흉내 낸다(`generator/search_engine.py`, 기존 σ 6.0 · 새 σ 1.4). 같은 후보·같은 라벨에서 그 정렬의 NDCG@10 을 재면(`ranker.sim_check`):

| 정렬 | NDCG@10 |
|---|---|
| 생성기 기존 랭킹(σ 6.0) | 0.621 |
| 기존 정렬 재현(인기순) | 0.570 |
| 생성기 새 랭킹(σ 1.4) | 0.745 |
| 이 순위 모델(교차 검증) | 0.873 |

학습 모델의 정렬 품질이 A/B 에 쓴 새 랭킹보다 높으므로, A/B 결과(검색 성공률 +20.7%p)는 이 모델 기준으로 보면 보수적인 쪽이다. 생성기의 검색어 해석은 이 폴더의 `query.py` 와 같은 규칙이다(검사 I11 이 검색어 2,139개 전부 같은 의도로 해석하는지 확인한다).

## 7. 한계

- 정렬 평가는 정식 이름 검색어만 대상이다. 해석이 맞게 연결되면 같은 정식 이름의 후보·피처로 채점되므로 정렬 품질도 같다고 본다.
- 라벨 후보는 배치마다 검색어당 최대 12개(노출 결과 + 확장 후보)라 전체 후보보다 좁다.
- 오프라인 NDCG 는 사람 라벨 기준이다. 실제 클릭·신청은 A/B(보고서 5~7단계)로 본다.
- 클릭 로그로 학습하려면 위치 편향 보정(노출 순위별 확인 확률 추정)이 필요해 이번에는 사람 라벨만 썼다.

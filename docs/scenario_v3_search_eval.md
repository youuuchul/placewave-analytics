# 시나리오 3.0 — 검색 품질 · 관련성 평가 운영 (2026-10-02 결정, 10-22 검색 모델 재설계)

시나리오 2.0 세계(서울 공간·이벤트 플랫폼 Placewave, 2025-09-22 ~ 2026-09-20)에 **검색 실패 → 관련성 평가 → 랭킹 개선 → 검색·신청 지표 변화**의 고리를 더한다. 모든 수치는 가상 시나리오와 분포 규칙으로 생성한다.

## 0. 원칙 — 검색 팀이 실제로 재는 방식으로 만든다

- **요청이 원천이다.** 검색 1건마다 서버가 요청 ID(`search_id`)를 발급하고 요청 로그(`raw.search_log`)를 남긴다. 결과 클릭은 서버 클릭 로그(`raw.search_click_log`)가 같은 요청 ID 로 남긴다. 검색 지표는 전부 이 두 로그에서 나온다. GA 이벤트(`search`·`select_search_result`)에도 같은 `search_id` 가 실리지만 수집 누락(약 1.5%)이 있어 지표 분모로 쓰지 않고 수집률 점검에만 쓴다.
- **행동과 검색을 같은 실행에서 만든다.** 세션 시뮬레이션이 검색할 때 검색 엔진 모델(`generator/search_engine.py`)을 부르고, 그 결과가 다음 화면을 정한다. 결과를 누르면 공간·행사 상세로 가고, 결과가 없거나 마음에 드는 결과가 없으면 재검색·검색 메인·홈·이탈로 간다. 그래서 랭킹이 바뀌면 클릭·재검색뿐 아니라 그 뒤의 상세 조회·신청·결제까지 바뀐다. 집계값만 만들거나 GA 행동을 고정한 채 서버 로그를 덧붙이지 않는다.
- **평가 도구 원천은 서버 로그를 읽어 만든다.** `generator/search_eval.py` 는 생성된 서버 로그·공간·행사 원장을 읽기만 하고 평가자·배치·과제·라벨 5표를 쓴다. 평가 후보와 정답 등급은 검색 엔진과 같은 참 관련도를 쓴다.
- **실험 일정은 세션 시작일로 고정한다.** 랭킹 버전과 재색인 회귀는 세션 시작일(KST)로 정하고 세션 도중 바뀌지 않는다. 마트의 날짜도 세션 시작일이라 A/B 기간·적용 이후 구간이 시나리오 날짜에서 섞이지 않는다.

## 2. 단일 세계 규칙

- 검색어(정식 이름)와 후보(공간·행사) 쌍의 **참 관련도 등급**(0 무관 · 1 약관련 · 2 관련 · 3 정확)을 속성 일치로 한 번 계산한다. 상권·장르·공간 유형·행사 유형·이름 일치와 거리가 근거다.
- 같은 참 등급을 세 곳이 공유한다.
  - 검색 엔진: 랭킹이 후보를 정렬하는 기준(v1 은 잡음이 커서 관련도와 거의 무관하게 섞이고, v2 는 라벨 학습으로 관련도에 가깝게 정렬)
  - 클릭 모델: 본 결과를 누를 확률
  - 평가 라벨: 평가자는 참 등급을 숙련도·지침 버전·피로도에 따른 잡음과 함께 관측한다
- 후보는 **그날 실제로 보이는 카탈로그**에서만 뽑는다. 공간은 등록 다음 날부터 폐업 전까지, 행사는 공개 다음 날부터 시작 전까지이고 개최 공간이 보일 때만.

## 3. 검색 엔진 모델 (`generator/search_engine.py`)

세션에서 검색이 일어날 때의 순서다.

1. **찾는 대상.** 장르 40% · 상권 25% · 행사 유형 15% · 공간명 20%(그날 조회 가중으로 고른 공간의 상호 첫 단어). 결과를 누르지 않고 다시 검색할 때 60% 는 같은 대상을 다른 입력으로 다시 찾는다.
2. **입력 변형.** 사람은 정식 이름만 치지 않는다. 장르·행사 유형은 줄임말·영문(`케이팝`·`kpop`·`재즈`·`팝업`), 상권은 정식 이름(구분자 `·` 포함) 62% · 띄어 쓴 이름 10% · 한 동네 이름, 공간명은 첫 단어 62% · 전체 상호 10% · 소문자 8% · 앞부분 5% · 오타 15%.
3. **해석.** v1 은 정식 이름과 글자가 같을 때만 찾는다. v2 는 소문자·공백·구분자를 정규화하고 동의어 사전과 공간명 앞부분 일치로 해석한다. 해석하지 못하면 결과 0건. 재색인 회귀(9/1~9/4, v2 색인)는 `·` 가 든 입력을 해석하지 못한다.
4. **검색·정렬.** 해석한 대상의 참 관련도 1 이상 후보가 결과다. 정렬 점수 = 참 관련도 + 잡음(v1 표준편차 6.0 · v2 1.4), 상위 10개를 노출한다. 실제로 학습한 순위 모델(`ranker/`, LightGBM LambdaRank)은 같은 후보·라벨에서 교차 검증 NDCG@10 0.873으로, 이 v2 정렬(0.745)보다 높다. 그래서 A/B 결과는 학습 모델 기준으로 보면 보수적인 쪽이다(`ranker/README.md` §6).
5. **클릭(캐스케이드).** 위에서부터 차례로 본다. k 위를 볼 확률 0.95 × 0.85^(k−1), 본 결과를 누를 확률은 참 관련도 3 · 2 · 1 · 0 에 0.30 · 0.10 · 0.02 · 0.01. 첫 클릭에서 멈추고, 끝까지 누르지 않으면 클릭 없음.
6. **다음 화면.** 클릭 → 그 공간·행사 상세(이후 일반 화면 전이로 신청·결제). 클릭 없음 → 세션 종료 결과 0건 35% · 결과는 있으나 클릭 없음 20%, 나머지는 검색 결과 화면의 기존 전이에서 상세를 뺀 분포(재검색·검색 메인·홈), 결과 0건이면 재검색 가중 ×1.8. 기존 전이에는 검색 결과·검색 메인 뒤 종료가 없어, 이탈이 없으면 실패한 검색도 재검색 끝에 같은 비율로 신청에 닿는다. 검색 품질이 신청까지 이어지는 고리가 이 규칙이다(검사: 결과를 누른 세션의 신청률 > 끝내 못 누른 세션).
7. **응답 시간.** 로그정규, 중앙값 v1 110ms · v2 124ms(동의어 확장·재정렬 비용).
8. **추천 슬롯.** 5/4 부터 결과가 있는 요청의 60% 에 파트너 공간 예정 행사 1건(절반은 검색 대상과 관련 있는 행사).

랭킹 배정: 7/13 이전 v1, 7/13~7/26 은 기기 ID MD5 앞 8자리 mod 2 = 1 이면 v2, 7/27 부터 v2. 기기 단위라 한 사람이 기기 두 대로 두 집단을 함께 볼 수 있다(결과 보고에 비율을 적는다).

## 4. 원천

### 4.1 검색 서버 로그 `raw.search_log` · `raw.search_click_log`

| 표 | 1행 | 열 |
|---|---|---|
| `search_log` | 검색 요청 | `request_id, requested_at(UTC), user_pseudo_id, ga_session_id, query_raw, query_intent(검색어 분류기: genre/region/event_type/venue_name/other), ranker_version, results_count, results ARRAY<STRUCT<position, item_type, item_id>>(상위 10), promoted_event_id, latency_ms` |
| `search_click_log` | 결과 클릭 | `request_id, clicked_at, position, item_type, item_id` |

- `query_intent` 는 랭킹과 별개인 분류기 결과다(동의어 사전으로 해석, 못 하면 `other`). 그래서 v1 에서 0건이 난 줄임말 입력도 의도 유형으로 나눠 볼 수 있다.
- GA 의 `search`·`select_search_result` 이벤트는 `search_id` 파라미터를 싣고, 1.5% 는 수집되지 않는다(서버 로그에는 남는다).

### 4.2 평가 도구 원천 `raw.eval_*`

| 표 | 1행 | 열 |
|---|---|---|
| `eval_raters` | 평가자 | `rater_id, rater_group(internal/vendor), joined_at, left_at, weekly_target` |
| `eval_batches` | 배치 | `batch_id, requester(search/promotion), purpose(train/eval/adhoc), guideline_version(v1/v2), target_tasks, labels_per_task, created_at, due_at, priority` |
| `eval_queries` | 배치에 편입된 검색어 | `batch_id, query_norm, source(failed/head/random — 검색팀, promoted — 프로모션 추천 슬롯), sampled_at` |
| `eval_tasks` | 검색어 × 후보 | `task_id, batch_id, query_norm, item_type, item_id, shown_position, ranker_version, is_gold, gold_grade` |
| `eval_labels` | 라벨 1건 | `label_id, task_id, rater_id, grade(0~3), submitted_at, handle_seconds, is_rework` |

- 대상 검색어: 직전 7일 서버 로그에서 실패 검색어(아래 정의) → 상위 검색량 → 무작위 순으로 뽑고, 배치 목적별 비율은 출처별 상한이라 모자란 몫은 다음 출처로 넘긴다.
- 과제 완료 = 라벨 수가 `labels_per_task` 에 도달. 정답셋 과제는 일반 과제와 같은 형태로 섞인다. 재작업 = 검수에서 반려되어 같은 평가자가 다시 제출한 라벨.
- 긴급 배치: 7/6 랭킹 v2 출시 전 검증(실패 40% · 상위 60%, 900과제), 9/1 프로모션(캠페인 추천 슬롯), 9/8 검색 회귀 검증(실패 80% · 상위 20%, 480과제, 마감 4일, 우선순위 1). 긴급 배치가 대기열 앞에 서서 같은 주 정기 배치가 마감 위험으로 밀린다.

## 5. 정의 (staging · marts)

### 5.1 staging

- `int_search` — 1행 = 서버 검색 요청. 클릭은 요청 ID 로 클릭 로그를 묶어 첫 클릭(순위·대상), 세션은 요청의 `ga_session_id` 로 `int_session` 에 붙이고 날짜는 세션 시작일. 재검색 = 결과를 누르지 않았고 같은 세션에 다음 요청이 있음. 세션의 첫 요청만 세션 단위 열(같은 세션 신청 도달)을 갖는다. GA 수집 여부(`ga_logged`)는 품질 확인용. 세그먼트 3축(`channel1`·`device_platform`·`member_seg`)
- `int_label` — 1행 = 라벨. 과제·배치·평가자 속성, 정답셋 일치 여부, 같은 과제 다른 라벨과의 쌍별 일치 수

### 5.2 marts

| 표 | 종류 | 그레인 | 쓰임 |
|---|---|---|---|
| `daily_search` | 지표 | 일 × 의도 유형 × 랭킹 버전 × 세그먼트 3축 | 검색 탭 스코어보드·추이·분해, 보고서(진행 점검·재색인 회귀) |
| `daily_query` | 리스트 | 일 × 정규화 검색어 × 세그먼트 3축 | 실패 검색어 표 |
| `exp_ranker_request` | 실험 | 요청 (세션 시작일 6/22~7/26) | A/B 설계서·진행 점검·결과 보고. 배정(`arm`)을 실험 전 기간에도 같은 규칙으로 붙여 A/A 비교와 기기 단위 분산 계산에 쓴다 |
| `weekly_eval_ops` | 지표 | 주 × 요청 부서 × 평가자 그룹 × 지침 버전 | 라벨링 운영 보고서 스코어보드·추이 |
| `weekly_rater` | 리스트 | 주 × 평가자 | 평가자 표·산점도 |
| `weekly_batch` | 리스트 | 주 × 배치 (주말 시점 누적) | 목표 대비 진척·마감 위험 |

- 비율은 마트에 저장하지 않는다. 일치도 카파도 분자·분모 성분(쌍 수·일치 쌍 수·등급별 라벨 수)으로 저장하고 화면에서 계산한다.
- **검색 성공률**(주 지표) = 결과를 1번 이상 누른 요청 ÷ 전체 요청 = (1 − 결과 0건 비율) × 결과 클릭률. 결과 0건이 줄어 결과 클릭률의 분모가 바뀌어도 이 지표는 요청 전체가 분모라 흔들리지 않는다.
- **실패 검색어** = 기간 안 검색 20건 이상이고 결과 0건 비율 30% 이상인 정규화 검색어(`metrics.json` Q09, 생성기·검사 C20 과 같은 기준).
- **평가 편입**(Q10) = 실패 검색어가 기간 시작 ~ 기간 끝 + 7일 안에 검색팀 배치에 들어감. 출처(실패·상위 검색량·무작위)는 가리지 않는다. 프로모션 추천 슬롯 배치는 추천 행사를 평가하므로 뺀다.

### 5.3 검사

- `daily_search` 검색 수 합 = `int_search` 행 수, 날짜별 (C16)
- 클릭 로그 행 = 중간 표 클릭 요청 수, 요청 로그에 없는 클릭 0건 (C21)
- 결과 0건 + 결과 있음 = 검색, 클릭 ≤ 결과 있음, 첫 클릭 순위 1~10 (I8)
- 실험 마트: 배정 규칙 재계산 일치, 실험 기간 받은 랭킹 = 배정, 기간 경계 (I9)
- GA 검색 이벤트 수집률 97~99.5% (R12)
- `weekly_eval_ops` 라벨 합 = `eval_labels` 행 수, 정답셋 정확도 성분 합 = `int_label` 재집계, 배치 누적 완료 ≤ 목표

## 6. 화면

- **검색 탭**: 스코어보드(검색 이용자·검색 성공률·결과 0건 비율·평균 첫 클릭 순위·재검색률·검색 세션 신청 전환) → 검색 성공률·결과 0건 비율 추이 → 의도 유형별 → 검색어 표(실패 검색어·평가 편입일). 실험 구간 표식·보고서 링크는 두지 않는다. 한 사업의 맥락이 있는 표시는 보고서 안에만 둔다.
- **보고서 `검색 품질 개선` 8단계**: 실패 검색어 발견 → 라벨링 운영(운영 대시보드) → 평가 지침 개정 → 순위 모델 설계·오프라인 평가 → A/B 설계서 → 진행 점검 → 결과 보고 → 재색인 회귀. 시점이 다른 문서는 나눠 쓴다. 주요 보고서(발견 · 순위 모델 · 결과 보고 · 재색인 회귀)는 목록에서 이름을 강조한다.
- **주간 브리핑**: 방문·검색 성공률 변화를 규칙 문장으로.

# 시나리오 3.0 — 검색 품질 · 관련성 평가 운영 (2026-10-02 결정)

시나리오 2.0 세계(서울 공간·이벤트 플랫폼 Placewave, 2025-09-22 ~ 2026-09-20)에 **검색 실패 → 관련성 평가 → 랭킹 개선 → 검색 지표 변화**의 고리를 더한다. 모든 수치는 가상 시나리오와 분포 규칙으로 생성한다.

## 0. 원칙 — 기존 원천을 바꾸지 않는다

- `raw.ga4_events`·`raw.db_*`·`raw.ads_spend` 와 기존 staging·marts 는 그대로 둔다. 기존 수치·검사 결과는 3.0 적용 전후로 같아야 한다.
- 새 원천 두 종류를 **부속 원천**으로 추가한다. 생성기 `generator/search_eval.py` 는 기존 GA 로그·공간·행사 원장을 **읽기만** 하고 새 파일만 쓴다.
  - 검색 서버 로그 `raw.search_log` — GA `search` 이벤트 1건마다 같은 요청의 서버 쪽 기록(결과 수·노출 목록·랭킹 버전)
  - 평가 도구 스냅샷 `raw.eval_*` 5표 — 관련성 평가 프로그램의 평가자·배치·대상·과제·라벨
- 이 방식의 제약을 그대로 둔다. GA 행동(검색 후 어느 화면으로 갔는가)은 고정이므로 **결과 클릭률과 검색 경유 신청 전환은 랭킹 버전에 따라 달라지지 않는다.** 랭킹 개선은 결과 0건 비율·클릭 순위·상위 노출 비율에서 보인다.

## 2. 단일 세계 규칙

- 검색어와 후보(공간·행사) 쌍의 **참 관련도 등급**(0 무관 · 1 약관련 · 2 관련 · 3 정확)을 속성 일치로 한 번 계산한다. 상권·장르·공간 유형·행사 유형·이름 일치가 근거다.
- 같은 참 등급을 두 원천이 공유한다.
  - 서버 로그: 랭킹이 후보를 정렬하는 기준(v1은 정확 일치 위주로 거칠게, v2는 참 등급에 더 가깝게)
  - 평가 라벨: 평가자는 참 등급을 숙련도·지침 버전·피로도에 따른 잡음과 함께 관측한다
- 결과 목록 후보는 **그날 실제로 보이는 카탈로그**(등록·운영 중 공간, 노출 중 행사)에서만 뽑는다.

## 3. 검색 서버 로그 `raw.search_log`

1행 = 검색 요청 1건.

| 열 | 내용 |
|---|---|
| `request_id` | 요청 키 |
| `requested_at` | 서버 수신 시각(UTC). GA `search` 이벤트 시각 기준 수백 ms 지연 |
| `user_pseudo_id` | 기기 키(GA 와 같은 체계) |
| `query_raw` | 입력 검색어 — GA `search_term` 과 같음 |
| `ranker_version` | `v1`·`v2`. 07-13~07-26 은 기기 해시 50% 버킷 |
| `results_count` | 일치 후보 수 |
| `results` | `ARRAY<STRUCT<position INT64, item_type STRING, item_id INT64>>` 상위 10 |
| `promoted_event_id` | 상단 추천 슬롯 행사(없으면 NULL) |
| `latency_ms` | 응답 시간 |

- **재색인 회귀(9/1~9/4)**: 구분자 `·` 가 든 검색어(상권) 요청 중 결과 클릭이 없던 요청의 90%를 결과 0건으로 둔다. 클릭이 있던 요청은 GA 행동이 고정이라 그대로다. 별도 난수열을 써서 9/1 이전 행과 다른 요청의 결과는 바뀌지 않는다. 9/5 핫픽스 뒤로는 평소 규칙
- GA 와 서버 로그는 공유 키가 없다. **기기 + 시각 근접(±3초)** 으로 매칭한다. 서버에만 있는 요청(GA 미수집)이 약 1~2% 있어 매칭률이 100% 가 아니다.
- 클릭은 GA 에서 판정한다. 검색 결과 화면 다음 화면이 공간·행사 상세면, 그 항목이 결과 목록에 있을 때 클릭으로 보고 그 `position` 을 클릭 순위로 쓴다. 생성기는 GA 에서 이어진 상세 항목을 결과 목록에 넣고, 순위는 랭킹 버전 규칙으로 정한다.
- 결과 0건은 다음 화면이 상세가 아닌 검색에서만 생긴다.
- 기존 GA 에서 검색 결과 화면 다음은 재검색 49% · 공간 상세 28% · 검색 메인 16% · 홈 7% 이고 세션 종료는 0건이다. 그래서 '검색 후 이탈' 지표는 두지 않고 실패는 0건·재검색으로 본다. 클릭 대상은 공간뿐이다(행사 상세 직행 없음).
- 의도 유형은 기존 검색어 4종(장르 · 상권 · 행사 유형 · 공간명)을 staging 에서 사전 일치로 분류한다.

## 4. 평가 도구 원천 `raw.eval_*`

| 표 | 1행 | 열 |
|---|---|---|
| `eval_raters` | 평가자 | `rater_id, rater_group(internal/vendor), joined_at, left_at, weekly_target` |
| `eval_batches` | 배치 | `batch_id, requester(search/promotion), purpose(train/eval/adhoc), guideline_version(v1/v2), target_tasks, labels_per_task, created_at, due_at, priority` |
| `eval_queries` | 배치에 편입된 검색어 | `batch_id, query_norm, source(failed/head/random — 검색팀, promoted — 프로모션 추천 슬롯), sampled_at` |
| `eval_tasks` | 검색어 × 후보 | `task_id, batch_id, query_norm, item_type, item_id, shown_position, ranker_version, is_gold, gold_grade` |
| `eval_labels` | 라벨 1건 | `label_id, task_id, rater_id, grade(0~3), submitted_at, handle_seconds, is_rework` |

- 대상 검색어 추출: 실패 검색어(아래 정의) 우선, 상위 검색량 검색어, 무작위 표본을 배치 목적별 비율로 섞는다.
- 과제 완료 = 라벨 수가 `labels_per_task` 에 도달. 정답셋 과제는 평가자에게 일반 과제와 같은 형태로 섞인다.
- 재작업 = 검수에서 반려되어 같은 평가자가 다시 제출한 라벨.
- 긴급 배치: 7/6 랭킹 v2 출시 전 검증(실패 40% · 상위 60%, 900과제), 9/1 프로모션(캠페인 추천 슬롯), 9/8 검색 회귀 검증(목표 비율 실패 출처 80% · 상위 20%, 480과제, 마감 4일, 우선순위 1). 비율은 출처별 상한이고 모자란 몫은 다음 출처로 넘긴다 — 9/8 은 직전 7일 실패 검색어가 9개(검색어당 과제 12개)뿐이라 실패 출처가 과제 108개(22.5%)를 채우고 나머지 372개는 상위 검색어로 채웠다. 긴급 배치가 대기열 앞에 서서 같은 주 정기 배치가 마감 위험으로 밀린다.
- 재생성 규칙: 회귀를 넣어도 배치 계획 다음의 라벨 시뮬레이션은 회귀가 없을 때와 같은 난수 지점에서 시작한다. 그래서 9/7 배치 이전의 배치·과제·라벨은 회귀 추가 전과 같다(10-19 재생성에서 비교 확인).

## 5. 정의 (staging · marts)

### 5.1 staging

- `int_search` — 1행 = 서버 검색 요청. GA 매칭 여부, 정규화 검색어(소문자·공백 정리), 의도 유형, 결과 수, 클릭 여부, 첫 클릭 순위, 재검색(결과 클릭 없이 바로 다음 검색이 이어짐), 같은 세션 신청 도달, 랭킹 버전, 사람 키, 세그먼트 3축(`channel1`·`device_platform`·`member_seg`, 기존 `int_session` 기준)
- `int_label` — 1행 = 라벨. 과제·배치·평가자 속성, 정답셋 일치 여부, 같은 과제 다른 라벨과의 쌍별 일치 수

### 5.2 marts

| 표 | 종류 | 그레인 | 쓰임 |
|---|---|---|---|
| `daily_search` | 지표 | 일 × 의도 유형 × 랭킹 버전 × 세그먼트 3축 | 검색 탭 스코어보드·추이·분해 |
| `daily_query` | 리스트 | 일 × 정규화 검색어 × 세그먼트 3축 | 실패 검색어 표 (행 수 확인 후 세그먼트 축 유지 여부 결정) |
| `weekly_eval_ops` | 지표 | 주 × 요청 부서 × 평가자 그룹 × 지침 버전 | 평가 운영 탭 스코어보드·추이 |
| `weekly_rater` | 리스트 | 주 × 평가자 | 평가자 표·산점도 |
| `weekly_batch` | 리스트 | 주 × 배치 (주말 시점 누적) | 목표 대비 진척·마감 위험 |

- 비율은 마트에 저장하지 않는다. 일치도 카파도 분자·분모 성분(쌍 수·일치 쌍 수·등급별 라벨 수)으로 저장하고 화면에서 계산한다 — 필터를 걸어도 합산이 성립한다.
- **실패 검색어** = 기간 안 검색 20건 이상이고 결과 0건 비율 30% 이상인 정규화 검색어(`metrics.json` Q09, 생성기·검사 C20 과 같은 기준).
- **평가 편입**(Q10) = 실패 검색어가 기간 시작 ~ 기간 끝 + 7일 안에 검색팀 배치에 들어감. 출처(실패·상위 검색량·무작위)는 가리지 않는다 — 상위 검색량 출처로 들어가도 검색 결과에 라벨이 붙어 랭킹 학습 재료가 되기 때문이다. 프로모션 추천 슬롯 배치(출처 promoted)는 추천 행사를 평가하므로 뺀다(10-19 정정: 실패 출처만 세면 평가 착수 전 28일 실패 검색어 20개 중 8개가 4/1 첫 배치에 상위 검색량 출처로 들어갔는데도 미편입으로 보였다). 실패가 반복된 검색어는 그 기간의 편입만 센다.

### 5.3 검사 추가

- `daily_search` 검색 수 합 = `int_search` 행 수, 날짜별
- 클릭 검색 ≤ 결과 있는 검색, 첫 클릭 순위 1~10
- GA–서버 매칭률 98% 이상(미달 시 생성기·조인 규칙 확인)
- `weekly_eval_ops` 라벨 합 = `eval_labels` 행 수
- 정답셋 정확도: 마트 성분 합 = `int_label` 재집계
- 배치 누적 완료 과제 ≤ 목표, 마감 지난 완료 배치는 과제당 라벨 수 = `labels_per_task`
- 평가 배치에 편입된 `failed` 검색어는 편입 직전 주에 실패 검색어 조건을 만족

## 6. 화면

| 탭 | 위치 | 질문 | 기간 컨트롤 | 세그먼트 줄 |
|---|---|---|---|---|
| 검색 | 퍼널 다음 | 검색이 어디서 실패하고, 랭킹 개선이 실패를 줄였는가 | 기간 프리셋 | 채널·플랫폼·회원 (마트 축 있음) |
| 평가 운영 | 주간·월간 앞 | 이번 주 평가 목표를 품질 기준 안에서 채우고 있는가, 막힌 곳은 어디인가 | 주차 선택기 | 요청 부서로 대체(평가자 그룹은 라벨 수 차트, 지침 버전은 비교 표에서 나눈다) |

- 검색: 스코어보드 → 0건 비율·클릭률 추이(랭킹 v2 노출·전체 적용 표시) → 의도 유형별·랭킹 버전별 분해 → 실패 검색어 표(평가 편입 여부)
- 평가 운영: 목표·진척 → 생산성 → 품질 → 평가자 표(처리량 × 정확도) → 지침 버전 비교
- 주간·월간 탭: 주간 브리핑(검색·평가 운영·기존 KPI 핵심 변화, 규칙 기반 문장)
